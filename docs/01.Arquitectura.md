# Arquitectura real

## Flujo principal

`Cliente -> order-service -> user-service -> inventory-service -> payment-service -> notification-service`

## Servicios

| Servicio | Puerto | Rol |
| --- | --- | --- |
| `order-service` | `8000` | Orquestador del flujo |
| `user-service` | `8001` | Validacion de usuarios desde `users.data` |
| `inventory-service` | `8002` | Disponibilidad, reserva y liberacion de `products` |
| `payment-service` | `8003` | Simulacion y persistencia en `payments` |
| `notification-service` | `8004` | Simulacion y persistencia en `notifications` |
| `postgres` | `5432` | Persistencia principal |
| `prometheus` | `9090` | Scraping de metricas |
| `grafana` | `3000` | Dashboards y Explore |
| `jaeger` | `16686` | Visualizacion de trazas |

## Base de datos

Tablas reales definidas en `db/init.sql`:

- `users`
- `products`
- `orders`
- `payments`
- `notifications`

## Red

Compose crea una red bridge:

- `resilencia-kubernetes_app-net`

## Observabilidad

- Cada microservicio expone `/metrics`
- OTLP sale hacia `otel-collector`
- Prometheus scrapea `microservices` y `otel-collector`
- Jaeger recibe trazas
- Grafana usa un datasource aprovisionado hacia Prometheus
